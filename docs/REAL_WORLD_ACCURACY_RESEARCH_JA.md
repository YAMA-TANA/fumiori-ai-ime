# AI-IME 実用精度調査

調査日: 2026-09-13  
対象: `yamatana-ai-ime`、Mozc実候補列、実行中のWindows版 `mozc_server.exe`

## 結論

現在の改善余地は、モデルの大型化よりも「Mozcが出した候補を、入力中の文脈と語全体で安全に選ぶ」部分に大きい。

優先順位は次の通り。

1. 実際のMozc候補を表記単位で重複除去し、上位候補をAIへ送る。
2. 1セグメントずつではなく、複数セグメントを小さな句ビームとして比較する。
3. 数詞・日付・助数詞・割合は、候補の並べ替えだけでなく限定的な構成器で扱う。
4. MozcよりAIが良い確信度を、前文脈・候補差・候補内部文脈で校正する。
5. 実際のTSF/アプリ入力経路でAI呼び出しが発生したことを確認できるスモークテストを追加する。

## 1. 実測方法

### Mozc候補生成

診断用の `mozc_converter_raw.exe` を使い、Mozcが実際に生成したセグメントと候補列を収集した。統制した52ケースでは、1セグメントの候補数は最小5、中央値36、平均57.35、最大355だった。

つまり、全候補をAIへ渡す設計は遅延・ノイズ・重複の影響を受けやすい。オフライン比較では候補上限8、表記重複除去、数字表記の代表候補補充を試した。

### 実利用を模した入力

通常の日本語入力では、変換時点で後続文脈が存在しない。そこで105場面を「対象語のみ」と「助詞・活用込み」に分け、前文脈だけを与える210件を作った。対象は日常、業務文書、IT、公共・医療、製造・物流、数値・固有表現である。

これは頻度重み付きの本番ログではなく、同音異義語を多く含む難問寄りの品質ベンチマークである。厳密一致と、`3時/三時` のような自然な表記揺れを許す実用正解を分けて評価した。

### 実行中Mozc

インストール済みの次のプロセスを確認した。

`C:\Program Files (x86)\Yamatana AI IME\mozc_server.exe`

MozcのセッションIPCへ接続し、`はな` を入力すると、実際に `花`、`鼻`、`華`、`端` などの候補列が返ることを確認した。したがって、研究の中心は人工的な候補リストではなくMozcの実出力である。

## 2. 数値結果

### 前文脈のみ・人間入力ベンチマーク

保存済みのCPU INT8結果（210件）:

| 指標 | Mozc素順位 | AI適用後 |
|---|---:|---:|
| 厳密一致 | 140/210 (66.7%) | 199/210 (94.8%) |
| 実用正解 | 152/210 (72.4%) | 210/210 (100.0%) |

安全ゲートは、Mozcが正しかった152件を全件維持し、Mozcが誤った58件を全件回復、回帰0件、タイムアウト0件だった。オフライン評価で候補上位8件の中に正解が存在したのは210/210件であり、このベンチマークでは候補生成より選択・校正が主問題だった。

ただし、この100%は現行のインストール済みMozc経路の実測値ではない。`human_prefix_benchmark_cpu_v12.json` の保存済み評価は `candidate_limit: 8` だが、現在のMozc側 `ai_rewriter.cc` は通常候補4件＋補助候補1件、最大5表記をAIへ送る実装である。したがって、現行バイナリの精度を100%と結論してはいけない。

この不一致を確認するため、同じ保存済みMozc候補を候補上限5・表記重複除去・CPU INT8で再評価した。オフラインの近似条件では実用正解208/210 (99.1%)、タイムアウト0件、回帰0件だった。これは8件条件の210/210より現行実装に近いが、なお実TSF/インストール済みバイナリのエンドツーエンド結果ではない。

分野別の実用正解は、公共・医療が7/20から20/20、業務・文書が40/56から56/56、日常・一般が34/50から50/50へ改善した。IT・開発は37/40から40/40、製造・物流は16/20から20/20だった。

### Mozc実候補パイプライン

GPU FP16の保存済み結果（52ケース、文脈別）:

| 文脈 | Mozc素順位 | AI後 | タイムアウト |
|---|---:|---:|---:|
| 前後 | 17/52 (32.7%) | 44/52 (84.6%) | 0 |
| 前方のみ | 17/52 (32.7%) | 44/52 (84.6%) | 0 |
| 後方のみ | 17/52 (32.7%) | 31/52 (59.6%) | 0 |
| 文脈なし | 17/52 (32.7%) | 18/52 (34.6%) | 0 |

代表的な回復は、`はな → 鼻/花`、`かみ → 紙/髪`、`しこう → 施行/試行/指向`、`だいごい → 第五位/第5位`、`さんにん → 三人/3人` である。

ただし、`天気の雨` を `あめ` としてしまう回帰も確認した。数字表記の好みを強く加点するだけでは、意味判定を壊す可能性がある。

## 3. Mozcを使って初めて分かった問題

### 候補数ではなく、異なる表記数で比較する必要がある

実候補には同じ表記の重複が多い。調査では4,224候補のうち、表記重複を除くと3,211候補で、1,013件（約24%）が重複だった。

「1位と2位のスコア差」をそのまま信頼すると、実質同じ表記同士を比較して確信度を低く見積もる。信頼度は異なる表記の最高候補同士で計算するべきである。

### 数詞はAI再順位付けだけでは解けない

`じゅうにこ → 12個` のように、正解表記がMozc候補にない場合は、並べ替えでは解決できない。`15日`、`2026年`、`第5位` も、セグメント境界をまたいで語全体を構成しないと `105日` のような誤結合が起きる。

一方、`一石二鳥`、`一期一会`、`第三者` のように漢数字を維持すべき固定語もある。数字化は一律加点ではなく、数詞・接尾辞・固定表現を検証する構造処理にする必要がある。

### セグメント独立処理は語全体を壊す

Mozcが `だい / ご / い` と分けた場合、各セグメントを独立にAI変換すると `第 / 魚 / 凍` のように語全体が壊れる。基準仮説 `第五位` と代替仮説 `第5位` を句として同時に採点する必要がある。

## 4. 推奨アーキテクチャ

```text
Mozc変換
  ↓
表記重複除去・上位候補・数字代表候補の補充
  ↓
数詞/固定語の構造候補を限定生成
  ↓
2〜4セグメントの小さな句ビーム
  ↓
前文脈 + 現在句 + 後文脈で一括AI採点
  ↓
Mozc基準との差・文脈量・候補内共通部分で安全ゲート
  ↓
句全体を採用、または句全体をMozcへロールバック
```

実装上は、現在の `ai_rewriter.cc` にある重複除去・補助候補・全体期限の方向性は妥当である。ただし候補送信数はオフライン評価の8件ではなく最大5件であり、主にセグメント単位で再順位付けしている。候補数を含めて、句ビームと句単位ロールバックを次の大きな改善対象にするべきである。

## 5. 最優先の追加検証

### A. 本番入力経路の接続確認

実行中MozcのIPC変換は確認できたが、今回の合成キー入力では `ai_ime_status.json` の `ime_requests` が増えず、AIランカー呼び出しを観測できなかった。原因候補は、合成入力が通常のTSF経路と異なること、文脈設定がホスト側で渡らないこと、またはAIリライターをスキップするオプションである。

これは精度問題以前に、実際のIMEでAIが呼ばれているかを検証できていないという意味である。メモ帳・ブラウザ・エディタの3環境で、入力→Space変換→確定までを行い、Mozc候補、AIステータス、レイテンシ、採用候補を同時記録するスモークテストを追加するべきである。

### B. 代表性のある評価データ

210件の固定ベンチは回帰検出に有用だが、実利用頻度を表さない。次は匿名化した実入力ログ、またはユーザーが訂正した候補だけを収集し、次の重みを持つ評価にする。

- 変換回数の多い短語・助詞付き語
- ビジネス文書とチャットの混在
- 数字・記号・英字の入力比率
- ユーザーが候補を選び直したケース
- 前文脈の長さとアプリ種別

指標は、単純正答率だけでなく、Mozc正解の保持率、Mozc誤りの回復率、意味破壊率、訂正キー数、p50/p95レイテンシ、タイムアウト率を記録する。

### C. CPU/GPU別の校正

保存結果ではCPUとGPUで閾値付近の順位が異なるケースがある。同じ閾値を共有せず、CPU INT8とGPU FP16を別々に校正する。また、AIが自信を持っていてもMozcと意味的に競合する場合は、変更量を抑える保守的なゲートを優先する。

## 6. 現時点の判断

「Mozcを捨ててAIに全文変換させる」方向は採用しない。Mozcは候補生成・辞書・境界・学習履歴を担い、AIは候補内の文脈選択を担うのが安全である。

次のリリース候補は、モデル変更より先に以下を完了させるべきである。

1. 実TSF経路でAI呼び出しが発生することを確認。
2. 句ビームと句全体ロールバックを実装。
3. 数詞・日付・助数詞の構成器を追加し、固定語を保護。
4. 訂正ログを含むホールドアウトで、意味破壊率とp95遅延を測る。
